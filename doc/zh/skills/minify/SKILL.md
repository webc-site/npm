# 产物体积缩减方法论

适用于任何经过摇树与压缩的 JS 产物。与具体项目、构建器、压缩器实现无关。

## 唯一度量

1. 以产物的真实文件字节数为唯一指标。源码行数、字符数、派生指标都不作数：
   字符数会掩盖多字节编码的开销，派生指标会被压缩器的重复模式统计干扰判断。
2. 字节数下降就是下降，上升就是上升。任何「理论上更小」的说法一律用实测裁决。

## 流程

1. 改前实测记基线。
2. 每轮只动一类优化点，改完立刻重新构建并实测对比，无收益即回退。
3. 行为测试是守门人：被测试否决的「聪明」优化果断回退，不迁就优化去改测试。
4. 多轮迭代之间，回头用 A/B 复审上一轮凭直觉保留的决定。

## 普适原则

1. 标识符、声明形式、代码排版不占产物体积——压缩后名字统一变短，
   排版全部抹平。占体积的只有三类：字面量（字符串、数字及其编码开销）、
   结构代码（函数定义本体、调用点、表键名）、数据表内容本身。
   优化就从这三类下手，别在命名和风格上省字节。
2. 分三层审计：数据层（表、常量、重复后缀）、代码层（重复的逻辑片段）、
   形态层（同样的逻辑用哪种语法表达）。同一份逻辑，三层的字节账各不相同，
   逐层扫一遍才不会漏。
3. 源码 DRY 不等于产物 DRY。构建器会内联常量、复制展开「看似复用」的写法，
   源码里只写一遍的公共子串，产物里可能重复多份。要在产物层去重，
   就让拼接发生在运行时（以参数、回调等间接形式），折叠不掉才算真去重。
4. 反过来，重复的结构代码是复用的候选：抽辅助函数、参数化工厂，
   消除的是 N 份重复字节，新增的只是一份函数体。是否划算仍以字节实测裁决，
   调用点太少或参数化开销太大时也可能不划算。
5. 语义合并由行为判定，不由代码相似度判定。两处逻辑长得一样不代表能合并：
   若差异藏在消费上下文里（同一节点在不同位置渲染不同），合并会改变输出。
6. 表示形态影响字节：与数字编码对齐的定长表用位置数组表达（空槽占位），
   比重复书写键名的字典形态省去全部键；查表分发优先于分支判断，
   表结构自文档且扩展时只加槽位。
7. 归一化优于同义冗余：行为完全一致的多个入口（同义命令、别名、变体拼写），
   在最早的公共关卡统一改写，下游表里只留一个条目。落点选在归一成本最低、
   又不影响其它分支的层。
8. 后缀、单位、前缀这类重复片段移出数据源：数据只存裸值，
   构建表时统一拼接，使用端零运行时判断。
9. 重构会连带暴露死代码：默认参数、无人读取的占位、表形态改变后不再引用的
   导入，改完一轮回头清理，这些通常是免费的字节。

## 检查清单

1. 数据里的重复后缀/单位/前缀，能否移入构建期拼接？
2. 有无行为一致的同义入口可在上游归一？
3. 分发字典能否换成与数字编码对齐的位置数组？
4. 公共长字符串在产物里出现几份？重复了就用运行时拼接折叠掉。
5. 相似的代码片段够不够抽函数的门槛（以实测字节说话）？
6. 有无死默认参数、死槽位、失效导入？
7. 转义、实体名、短方法形式，是否选了实测更短的写法？

## 一句话原则

真实字节是唯一标准；数据、代码、形态三层各自有账，直觉只负责提出候选，
实测和行为测试负责裁决一切。
